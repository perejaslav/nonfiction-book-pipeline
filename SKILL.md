# NonFiction Pipeline (NFP)

## Обзор

NFP — это многостадийный pipeline для создания длинных научно-популярных текстов (книг 60–80K слов) с помощью параллельных субагентов. Он разбивает задачу на 5 этапов: **Intake → Foundation → Drafting → Expansion → Assembly**, каждый из которых производит конкретные артефакты на диске.

## Архитектура

```
User Input (тема/запрос)
    ↓
Intake — создаёт проект-директорию
    ↓
Foundation — thesis.md, structure.md, voice.md, terms.md, facts.json
    ↓
Drafting — параллельная запись глав (2–3 на субагента)
    ↓
Expansion — доработка отсутствующих/коротких глав
    ↓
Assembly — сборка manuscript.md, вёрстка PDF
```

---

## Этап 1. Intake

**Вход:** запрос пользователя (тема, структура, желаемый объём).
**Выход:** `intake.json` + директория проекта.

```bash
mkdir -p /root/hermes-nonfiction-pipeline/{foundation,chapters,drafts,assets/{images,tables,maps},scripts,templates}
```

Создать `intake.json`:
```json
{
  "title": "Название книги",
  "subject": "Тема",
  "thesis": "Центральный тезис в 1-3 предложения",
  "target_word_count": 70000,
  "target_chapters": 16,
  "language": "ru",
  "audience": "широкая, но интеллектуальная"
}
```

## Этап 2. Foundation

**Выход:** 5 файлов в `/foundation/`. Это единственный источник истины для всех субагентов.

### 2.1 thesis.md
Центральный тезис + 3–5 подтезисов. Должен ответить на вопрос «почему эта книга нужна и что читатель вынесет из неё».

### 2.2 structure.md
План всех глав с полями:
- `### Ch.XX: Название`
- `**Тезис:** ...` — тезис главы
- `**Объём:** ~XXXX слов` — целевой объём
- `**Ключевые факты:** fact_XXX` — ссылки на facts.json
- `**Содержание:**` — нумерованный список подтем

### 2.3 voice.md
Стилистический гид: тон, предложения, запреты, примеры неправильной/правильной формулировки.

### 2.4 terms.md
Таблица обязательных терминов + стилистические правила (camelCase, курсив при первом упоминании, запрет на анахронизмы и пр.).

### 2.5 facts.json
JSON-массив ключевых фактов с полями:
```json
{
  "id": "fact_001",
  "category": "date|name|term|event",
  "claim": "Утверждение",
  "source_type": "primary|secondary",
  "source_ref": "Краткая ссылка",
  "confidence": "high|medium|low",
  "verified": true|false,
  "verification_method": "peer_review|primary_source|search_harvester",
  "verification_note": "Дополнительный комментарий (опционально)"
}
```

**Правила confidence:**
- `high` — установленный факт из первоисточника или консенсуса современной историографии. Можно использовать без оговорок.
- `medium` — вероятный, но спорный факт или интерпретация. Использовать с маркером неопределённости: «по некоторым сведениям...», «вероятно...».
- `low` — гипотеза, легенда или единственный источник без подтверждения. **Не использовать как факт** в тексте. Можно упомянуть как гипотезу.

**Субагент обязан** перед написанием главы проверить все связанные с ней facts по полям `confidence` и `verified`.

### 2.6 Адаптация при наличии готового синопсиса

Если пользователь предоставил **детальный синопсис-план** (с тезисом, структурой всех глав, ключевыми сюжетами, оживляющими примерами и авторскими заметками), Foundation-фаза не генерируется с нуля, а **извлекается из синопсиса**:

- **thesis.md** — центральный тезис и подтезисы из раздела «Концепция и позиционирование» / «Ключевые тезисы»
- **structure.md** — каждая глава синопсиса содержит «Ключевые моменты для раскрытия» → преобразуются в разделы structure.md с тезисами, объёмом и ссылками на facts.json
- **voice.md** — из авторских заметок в синопсисе (тональность, стилистические указания); если синопсис ссылается на конкретного автора/стиль (например, «в духе Тома Холланда»), зафиксировать это
- **terms.md** — извлечь термины из текста синопсиса
- **facts.json** — каждый «Ключевой момент» и «Оживляющий пример» порождает один или несколько фактов

Сам синопсис скопировать в `assets/synopsis.md` как referencе для субагентов.

## Этап 3. Drafting

**Вход:** foundation-файлы.
**Выход:** файлы глав в `/chapters/ch_XX.md`.

### 3.1 Правило разбивки
Не более **2–3 главы на одного субагента**.
Причина: таймаут субагента 900 с. для 4+ глав слишком тесто.

### 3.2 Prompt-шаблон для субагента
Каждому субагенту даётся:
1. Цель: написать главы N–M
2. Контекст: пути к всем foundation-файлам
3. Толковое задание по каждой главе (тезис, объём, ключевые факты, структура)
4. Указание: первое предложение главы — мост от предыдущей, последнее — мост к следующей
5. Требование к стилю: соблюдать voice.md и terms.md
6. Формат сохранения: `/chapters/ch_XX.md`

**Фактологическая дисциплина (CRITICAL — HARD REQUIREMENTS):**

1. **Поля confidence и verified в facts.json — обязательны к проверке.** Перед написанием главы прочитай все facts, связанные с этой главой. Если `confidence: low` или `verified: false` — не используй этот факт как установленный. Можешь упомянуть как гипотезу с маркером «по некоторым сведениям...».

2. **Имена второстепенных персонажей:** не выдумывать. Если имя не фигурирует в facts.json и не из широко известного источника — проверить через любой доступный поисковый инструмент (Search Harvester, web_search с Brave/DuckDuckGo/Tavily, browser и т.д.). Если не подтверждается — оставить анонимным: «один коптский чиновник», а не «Пафнутий».

3. **Цитаты в кавычках:** прямая речь допускается ТОЛЬКО если это документированная цитата из установленного первоисточника (ат-Табари, Иоанн Никиусский и т.п.). Все реконструкции должны быть помечены маркерами гипотетичности: «вероятно, сказалось бы...», «по преданию...», «арабские хронисты описывают диалог как...».

4. **Точные числа:** не указывать конкретные цифры (высота стен, количество воинов, объём цистерн, суммы налогов) без ссылки на facts.json. Если цифра отсутствует в facts.json — использовать приблизительные обозначения: «несколько тысяч», «около полутора", а не «4 356 воинов». Не исправлять цифры из тренинговых данных в конкретные.

5. **Папирусные находки:** не ссылаться на конкретный документ без указания номера в каталоге или публикации. Допустимо: «папирусные документы свидетельствуют...». Недопустимо: «папирус Пафнутия гласит...» без проверки.

6. **Хронология:** если историческое лицо упоминается в контексте, отличном от его известной жизни (например, врач при армии после своей смерти) — проверить дату смерти. Если сомнения остаются — убрать этот персонаж из данного контекста.

7. **Пример из реального кейса:** аль-Харис ибн Калада (ум. 634) не может быть врачом при армии Амра (639–642). Вавилон основан Диоклетианом (ок. 300), а не Траяном. Стены высотой 10 м, а не 18. Если сумневаешь — проверь.

### 3.3 Запуск
Использовать `delegate_task` с `tasks=[...]` — каждая задача на свои главы. Максимум concurrent — `delegation.max_concurrent_children` (default 3).

### 3.4 Обработка таймаутов (двухволновая стратегия)

Таймаут субагента (900 с) — **нормальное событие**, не ошибка. NFP использует двухволновую стратегию:

**Волна 1 — Drafting:** запустить 4–6 субагентов с 2–3 главами каждый. Почти гарантированно часть или все таймаутнутся. Это ожидаемо.

После Волны 1:
1. Проверить `ls chapters/` — какие файлы успели записаться до таймаута
2. Проверить объём каждого файла скриптом подсчёта слов
3. Определить: отсутствующие файлы (не начаты) и недобравшие (<80% цели)

**Волна 2 — Expansion:** запустить новую партию субагентов для:
- Отсутствующих глав — написать с нуля, указав цель
- Недобравших глав — прочитать существующий текст, определить пробелы по structure.md, дописать новые разделы в **конец** файла. Важно: передать субагенту путь к существующему файлу и явно запретить удалять существующий текст.

## Этап 4. Expansion & Verification (она же Волна 2)

**Вход:** сырые черновики (после Волны 1).
**Выход:** доработанные и верифицированные главы.

Expansion запускается **всегда** — это не опциональный этап, а обязательная часть двухволновой стратегии. Первая волна почти гарантированно оставляет пробелы.

### 4.1 Проверка качества (объём)
Запустить скрипт подсчёта слов:
```python
import re, os
def count_words(path):
    text = open(path).read()
    return len(re.findall(r'[\\u0400-\\u04FF\\w]+', re.sub(r'[#*>|]', ' ', text)))
```

### 4.2 Определить дефицит
- Отсутствующие файлы (обработал не все субагенты)
- Главы с отклонением >20% от цели (structure.md прописал объём)

### 4.3 Доработка
Запустить дополнительных субагентов с заданием:
- Для отсутствующих — написать с нуля по foundation
- Для коротких — прочитать существующий текст, определить недостающие разделы по structure.md, дописать, сохранить стиль и хорошие фрагменты.

### 4.4 Фактологическая верификация (Spot-check)

**Почему это необходимо:** Субагенты склонны галлюцинировать «оживляющие примеры» — конкретные имена второстепенных персонажей, цитаты из несуществующих папирусов, точные цифры без источника, хронологические привязки реальных лиц к неверным событиям. В научно-популярной книге это недопустимо.

После Expansion провести выборочную верификацию по **5–10 наиболее подозрительным местам**:

**Что проверять в первую очередь (ранжировано по риску):**
1. **Прямая речь в кавычках** — если это не прямая цитата из известного источника (ат-Табари, Иоанн Никиусский), а «реконструкция слов исторического лица» — почти гарантированно галлюцинация. В научпопе допустима как стилистический приём, но должна быть явно помечена (например, словом «вероятно» или сноской).
2. **Имена второстепенных персонажей** — если имя не из foundation/facts.json и не из широко известного источника — проверить через Search Harvester или веб-поиск.
3. **Точные цифры** (высота стен, количество воинов, суммы дани, объём цистерн) — если нет ссылки на источник — проверить. Субагенты склонны завышать/занижать.
4. **Хронологическая привязка** — реальное историческое лицо может быть приписано к неверному периоду (например, врач, умерший за 5 лет до событий, «лечит армию»).
5. **Ссылки на несуществующие папирусные находки** — субагенты любят генерировать «коптские папирусы из Фаюма» с вымышленным содержанием.

**Инструмент верификации:** любой доступный поисковый инструмент или браузер. Возможные варианты ( зависят от конфигурации Hermes и прав пользователя):
- `web_search` (Brave Search, DuckDuckGo, Tavily, Google — зависит от провайдера)
- `browser` (поиск через браузер-автоматизацию)
- Search Harvester (локальный SearXNG + adapter, если установлен на машине)
- `web_extract` (для глубокой проверки конкретной страницы)

Отправлять конкретные запросы и проверять результаты по авторитетным источникам (Wikipedia, JSTOR, академические публикации, архивы университетов).

**Если галлюцинация подтвердилась:**
- Исправить факт (через patch к chapter-файлу)
- Или перевести в режим гипотезы («по некоторым сведениям...», «возможно...»)
- Или удалить (если не влияет на нарратив)

**Типичные паттерны галлюцинаций (из реального кейса «Арабское завоевание Египта»):**
- Имя реального исторического лица приписано к неверному событию: аль-Харис ибн Калада (ум. 634) назван врачом при армии Амра (поход 639–642). 
- Числовые параметры завышены: стены Вавилона названы «18 метров» (реально 10 м), диаметр башен «15 м» (реально 31 м), дата основания сдвинута с Диоклетиана (ок. 300) на Траяна (нач. II в.).
- «Папирус Пафнутия» с письмом «арабы уже здесь, ничего страшного» — полностью сгенерирован, не существует.
- «Псате с 13 свиньями» — жанр папируса реален, конкретный документ не идентифицирован.

## Этап 5. Assembly

**Вход:** готовые главы.
**Выход:** `book.pdf`.

### 5.1 Сборка manuscript.md
Использовать скрипт или `pandoc`:
1. YAML frontmatter (заголовок, автор, дата, язык, геометрия)
2. `\newpage` между главами
3. `\part*` перед каждой частью
4. TOC (оглавление) — `--toc`

### 5.2 PDF
```bash
pandoc manuscript.md -o book.pdf --pdf-engine=xelatex \
  -V mainfont="DejaVu Serif" \
  -V geometry:margin=2.5cm \
  -V fontsize=12pt -V linestretch=1.3 \
  -V papersize=a4 --toc
```

**Выбор шрифта:** для книг, содержащих нестандартные Unicode-символы (коптские, древнегреческие, иврит, арабские диакритики), используйте FreeSerif вместо DejaVu Serif. FreeSerif имеет более широкое покрытие Unicode и корректно отображает коптские глифы (U+2C80–U+2CFF). DejaVu Serif даёт больше страниц при том же объёме текста.

### 5.3 Сборка через скрипт (рекомендуется для книг с частями)

Вместо ручной конкатенации используйте Python-скрипт `scripts/build_manuscript.py`, который:
- Вставляет `\part{}` перед каждой частью
- Добавляет `\newpage` между главами
- Генерирует YAML frontmatter с метаданными
- Позволяет задать последовательность (части + главы)

### 5.3 Проверка
```bash
pdfinfo book.pdf
```
Должно быть: страниц ~250–350 при объёме 60–80K слов.

## Питфоллы

1. **Таймауты субагентов** — самая частая проблема. Даже при 2–3 главах на субагента время 900 с может быть недостаточным. **Не паниковать:** это ожидаемо. Перейти к Expansion (Волна 2), проверить chapters/ на частичные файлы.
2. **Отсутствие foundation** — без voice/terms/facts субагенты пишут в разном ключе.
3. **Повторы** — при расширении главы не удалять существующий текст, только дополнять.
4. **Мосты между главами** — обязательны для плавности; проверить в самом конце.
5. **Шрифты в PDF** — если DejaVu не установлен, заменить на Liberation Serif или Noto Serif. Для книг с нелатинскими/некириллическими скриптами (коптский, греческий, иврит) использовать FreeSerif.
6. **Синопсис от пользователя** — если он детальный, фаундейшн извлекается, а не пишется с нуля. Скопировать синопсис в assets/synopsis.md как референс для субагентов.
7. **Проверка после таймаута** — всегда проверяй `ls chapters/` перед перезапуском: файлы, успевшие записаться до таймаута, остаются на диске.
8. **Запрет удаления в expansion** — явно указывай субагенту: «Ничего не удаляй из существующего текста. Только дописывай новые разделы в конец». Без этой инструкции субагенты могут переписать главу заново.
9. **Галлюцинации в «оживляющих примерах»** — субагенты склонны генерировать вымышленные имена, папирусные цитаты, точные числа без источника. Всегда проводить Spot-check верификацию (см. Этап 4.4). Особенно уязвимы: прямая речь в кавычках, имена второстепенных персонажей, точные цифры, хронологическая привязка реальных лиц.
10. **Заголовки разделов в TOC** — если внутри глав используются подзаголовки вида `## I`, `## II`, Pandoc выведет в оглавление «I», «II» — бессмысленно. Всегда давать разделам содержательные названия: `## I. Смерть Ираклия: три акта трагедии`. Проверить перед финальной сборкой manuscript.md через `grep "^## "`.
11. **Сборка через скрипт (рекомендуется)** — при ручной конкатенации легко пропустить `\part{}` разрывы между частями книги. Использовать `scripts/build_manuscript.py` с явным списком последовательности. Проверить `grep "^# Глава\|^\\\\part" manuscript.md` после сборки.

## Publishing the Pipeline as a GitHub Repository

To publish the finished pipeline (or any derived book project) as a public repo:

1. **Prepare local structure** (README, LICENSE, .gitignore, docs/, templates/, examples/, scripts/).
2. **Create repo via GitHub API:**
   ```bash
   curl -s -X POST \
     -H "Authorization: token $GITHUB_TOKEN" \
     https://api.github.com/user/repos \
     -d '{"name":"nonfiction-book-pipeline","description":"...","private":false}'
   ```
3. **Push from a headless/VPS environment** — use a token-embedded remote URL to avoid interactive credential prompts (see `github-repo-management` skill, "Pitfall: Non-interactive environments").
4. **Verify** via API: `GET /repos/{user}/{repo}/contents/`.

See `references/github-publish.md` for a full copy-paste recipe.
