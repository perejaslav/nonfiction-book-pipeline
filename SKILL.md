# NonFiction Pipeline (NFP)

## Обзор

NFP — это многостадийный pipeline для создания длинных научно-популярных текстов (книг 60–80K слов) с помощью параллельных субагентов. Он разбивает задачу на 5 этапов: **Intake → Foundation → Drafting → Expansion → Assembly**, каждый из которых производит конкретные артефакты на диске.

## Архитектура

```
User Input (тема/запрос)
    ↓
Intake — создаёт проект-директорию
    ↓
Foundation — thesis.md, structure.md, voice.md, terms.md, facts.json
    ↓
Drafting — параллельная запись глав (2–3 на субагента)
    ↓
Expansion — доработка отсутствующих/коротких глав
    ↓
Assembly — сборка manuscript.md, вёрстка PDF
```

---

## Этап 1. Intake

**Вход:** запрос пользователя (тема, структура, желаемый объём).
**Выход:** `intake.json` + директория проекта.

```bash
mkdir -p /root/hermes-nonfiction-pipeline/{foundation,chapters,drafts,assets/{images,tables,maps},scripts,templates}
```

Создать `intake.json`:
```json
{
  "title": "Название книги",
  "subject": "Тема",
  "thesis": "Центральный тезис в 1-3 предложения",
  "target_word_count": 70000,
  "target_chapters": 16,
  "language": "ru",
  "audience": "широкая, но интеллектуальная"
}
```

## Этап 2. Foundation

**Выход:** 5 файлов в `/foundation/`. Это единственный источник истины для всех субагентов.

### 2.1 thesis.md
Центральный тезис + 3–5 подтезисов. Должен ответить на вопрос «почему эта книга нужна и что читатель вынесет из неё».

### 2.2 structure.md
План всех глав с полями:
- `### Ch.XX: Название`
- `**Тезис:** ...` — тезис главы
- `**Объём:** ~XXXX слов` — целевой объём
- `**Ключевые факты:** fact_XXX` — ссылки на facts.json
- `**Содержание:**` — нумерованный список подтем

### 2.3 voice.md
Стилистический гид: тон, предложения, запреты, примеры неправильной/правильной формулировки.

### 2.4 terms.md
Таблица обязательных терминов + стилистические правила (camelCase, курсив при первом упоминании, запрет на анахронизмы и пр.).

### 2.5 facts.json
JSON-массив ключевых фактов с полями:
```json
{
  "id": "fact_001",
  "category": "date|name|term|event",
  "claim": "Утверждение",
  "source_type": "primary|secondary",
  "source_ref": "Краткая ссылка",
  "confidence": "high|medium|low",
  "verified": true|false,
  "verification_method": "peer_review|primary_source|search_harvester",
  "verification_note": "Дополнительный комментарий (опционально)"
}
```

### 2.5A entities.md — реестр сущностей (обязателен для исторических книг)

Для исторического научпопа `terms.md` недостаточно: нужно отдельно фиксировать людей, города, институты, должности, династии, божества, тексты, артефакты и специальные термины. Это предотвращает ошибки вида «правильный термин в неправильной роли».

Формат:
```md
# Entities Registry

## People
### Имя / варианты имени
Type: ruler|priest|scholar|general|author|mythic figure
Period: ...
Role: ...
Do:
- как использовать в книге
Do not:
- запретные связки, анахронизмы, неподтверждённые роли
Source: fact_XXX

## Places
### Город / регион
Period: ...
Associated entities: ...
Do / Do not: ...

## Specialist terms
### Термин
Meaning: ...
Safe generic fallback: ...
Do not: ...
```

**Правило:** если субагент хочет использовать редкий термин, имя археолога, конкретный документ, городского покровителя, должность или мифологическую сущность — это должно быть в `entities.md` или `facts.json`. Если отсутствует, использовать более общее описание: «археологи», «храмовый служитель», «городской бог-покровитель», «поздний источник», «один из текстов».

### 2.5B fact_risk_map.md — карта фактологических рисков

Перед drafting создать карту потенциально опасных утверждений. Она нужна не для полноты, а для предотвращения публично заметных ошибок.

Формат:
```md
# Fact Risk Map

## High-risk claims
- Claim: «..."
  Risk type: absolute_first|exact_number|named_specialist|direct_influence|anachronism|specialist_term|quote|artifact
  Why risky: ...
  Safer wording: ...
  Status: allow_with_caveat|forbid|needs_source
  Source: fact_XXX / external check needed
```

Типовые high-risk зоны:
- «первый», «древнейший», «впервые в истории»;
- точные цифры без источника;
- имена второстепенных специалистов, экспедиций, папирусов, табличек, музейных объектов;
- прямые линии влияния между культурами и религиями;
- редкие должности и термины;
- реконструированная прямая речь;
- археологические находки с конкретным местом;
- анахроничные метафоры.

### 2.5C reconstruction_policy.md — политика цитат и реконструкций

Обязателен для книг с нарративными сценами.

```md
# Reconstruction Policy

## Direct quote
Кавычки использовать только если есть первоисточник/перевод и ссылка в facts.json.

## Paraphrase
Пересказ источника маркировать: «текст описывает...», «в хронике говорится...», «миф передаёт...». 

## Author reconstruction
Авторскую сцену маркировать: «можно представить...», «вероятно...», «в поэтической реконструкции...», «если восстановить ситуацию по косвенным данным...». 

Forbidden:
- выдавать стилизацию за прямой перевод;
- придумывать прямую речь исторических лиц;
- ставить реконструированные слова в кавычки без явной маркировки.
```

**Правила confidence:**
- `high` — установленный факт из первоисточника или консенсуса современной историографии. Можно использовать без оговорок.
- `medium` — вероятный, но спорный факт или интерпретация. Использовать с маркером неопределённости: «по некоторым сведениям...», «вероятно...».
- `low` — гипотеза, легенда или единственный источник без подтверждения. **Не использовать как факт** в тексте. Можно упомянуть как гипотезу.

**Субагент обязан** перед написанием главы проверить все связанные с ней facts по полям `confidence` и `verified`.

**Specialist term quarantine:** редкие исторические, религиоведческие, юридические, военные, археологические и филологические термины не вводить ради эффекта. Если термин не проверен — заменить точным общим описанием. Лучше «храмовый писец, наблюдавший за небом», чем неверный технический термин; лучше «защитная фигурка», чем неправильно названное мифологическое существо.

**No named specialist without source:** имена археологов, переводчиков, экспедиций, документов, табличек, музейных инвентарных номеров и конкретных артефактов допускаются только при наличии записи в `facts.json`/`entities.md` или быстрой проверки. Если источника нет — использовать обобщённую формулу.

### 2.6 Адаптация при наличии готового синопсиса

Если пользователь предоставил **детальный синопсис-план** (с тезисом, структурой всех глав, ключевыми сюжетами, оживляющими примерами и авторскими заметками), Foundation-фаза не генерируется с нуля, а **извлекается из синопсиса**:

- **thesis.md** — центральный тезис и подтезисы из раздела «Концепция и позиционирование» / «Ключевые тезисы»
- **structure.md** — каждая глава синопсиса содержит «Ключевые моменты для раскрытия» → преобразуются в разделы structure.md с тезисами, объёмом и ссылками на facts.json
- **voice.md** — из авторских заметок в синопсисе (тональность, стилистические указания); если синопсис ссылается на конкретного автора/стиль (например, «в духе Тома Холланда»), зафиксировать это
- **terms.md** — извлечь термины из текста синопсиса
- **facts.json** — каждый «Ключевой момент» и «Оживляющий пример» порождает один или несколько фактов

Сам синопсис скопировать в `assets/synopsis.md` как referencе для субагентов.

## Этап 3. Drafting

**Вход:** foundation-файлы.
**Выход:** файлы глав в `/chapters/ch_XX.md`.

### 3.1 Правило разбивки
Не более **2–3 главы на одного субагента**.
Причина: таймаут субагента 900 с. для 4+ глав слишком тесто.

### 3.2 Prompt-шаблон для субагента
Каждому субагенту даётся:
1. Цель: написать главы N–M
2. Контекст: пути к всем foundation-файлам
3. Толковое задание по каждой главе (тезис, объём, ключевые факты, структура)
4. Указание: первое предложение главы — мост от предыдущей, последнее — мост к следующей
5. Требование к стилю: соблюдать voice.md и terms.md
6. Формат сохранения: `/chapters/ch_XX.md`

**Фактологическая дисциплина (CRITICAL — HARD REQUIREMENTS):**

1. **Поля confidence и verified в facts.json — обязательны к проверке.** Перед написанием главы прочитай все facts, связанные с этой главой. Если `confidence: low` или `verified: false` — не используй этот факт как установленный. Можешь упомянуть как гипотезу с маркером «по некоторым сведениям...».

2. **Entities registry обязателен.** Перед использованием имён, городов, титулов, божеств, должностей, археологических объектов, специальных терминов и связок «город ↔ покровитель», «лицо ↔ событие», «термин ↔ функция» проверь `entities.md`. Если сущность отсутствует — либо проверь источник, либо используй обобщённую формулу.

3. **Имена второстепенных персонажей и специалистов:** не выдумывать. Если имя не фигурирует в facts.json/entities.md и не из широко известного источника — проверить через доступный поисковый инструмент. Если не подтверждается — оставить анонимным: «один чиновник», «один хронист», «археологи», а не конкретное имя.

4. **Цитаты в кавычках:** прямая речь допускается ТОЛЬКО если это документированная цитата из установленного первоисточника. Все реконструкции должны быть помечены маркерами гипотетичности: «вероятно...», «по преданию...», «хронист описывает...», «в поэтической реконструкции...».

5. **Точные числа:** не указывать конкретные цифры (высота стен, количество воинов, объём цистерн, суммы налогов) без ссылки на facts.json. Если цифра отсутствует в facts.json — использовать приблизительные обозначения: «несколько тысяч», «около...», «по некоторым оценкам...». Не превращать приблизительные данные в точные.

6. **Конкретные находки и документы:** не ссылаться на папирус, табличку, надпись, статую, печать, инвентарный номер или музейный объект без указания источника/каталога. Допустимо: «документы свидетельствуют...». Недопустимо: «табличка X гласит...» без проверки.

7. **Хронология:** если историческое лицо упоминается в контексте, отличном от его известной жизни — проверить даты. Если сомнения остаются — убрать персонажа из данного контекста.

8. **Абсолютные первенства:** формулы «первый», «древнейший», «впервые в истории» использовать только при high-confidence источнике и чётком критерии. Иначе заменять на «один из первых известных», «один из древнейших», «одни из ранних письменных свидетельств».

9. **Редкие термины:** если термин красивый, но роль не подтверждена, не используй его. Замени на точное общее описание: «жрец-писец», «храмовый служитель», «городской покровитель», «защитная фигурка», «ритуальный специалист».

10. **Пример из реального кейса:** аль-Харис ибн Калада (ум. 634) не может быть врачом при армии Амра (639–642). Вавилон основан Диоклетианом (ок. 300), а не Траяном. Стены высотой 10 м, а не 18. Если сомневаешься — проверь.

### 3.3 Запуск
Использовать `delegate_task` с `tasks=[...]` — каждая задача на свои главы. Максимум concurrent — `delegation.max_concurrent_children` (default 3).

### 3.4 Обработка таймаутов (двухволновая стратегия)

Таймаут субагента (900 с) — **нормальное событие**, не ошибка. NFP использует двухволновую стратегию:

**Волна 1 — Drafting:** запустить 4–6 субагентов с 2–3 главами каждый. Почти гарантированно часть или все таймаутнутся. Это ожидаемо.

После Волны 1:
1. Проверить `ls chapters/` — какие файлы успели записаться до таймаута
2. Проверить объём каждого файла скриптом подсчёта слов
3. Определить: отсутствующие файлы (не начаты) и недобравшие (<80% цели)

**Волна 2 — Expansion:** запустить новую партию субагентов для:
- Отсутствующих глав — написать с нуля, указав цель
- Недобравших глав — прочитать существующий текст, определить пробелы по structure.md, дописать новые разделы в **конец** файла. Важно: передать субагенту путь к существующему файлу и явно запретить удалять существующий текст.

## Этап 4. Expansion & Verification (она же Волна 2)

**Вход:** сырые черновики (после Волны 1).
**Выход:** доработанные и верифицированные главы.

Expansion запускается **всегда** — это не опциональный этап, а обязательная часть двухволновой стратегии. Первая волна почти гарантированно оставляет пробелы.

### 4.1 Проверка качества (объём)
Запустить скрипт подсчёта слов:
```python
import re, os
def count_words(path):
    text = open(path).read()
    return len(re.findall(r'[\\u0400-\\u04FF\\w]+', re.sub(r'[#*>|]', ' ', text)))
```

### 4.2 Определить дефицит
- Отсутствующие файлы (обработал не все субагенты)
- Главы с отклонением >20% от цели (structure.md прописал объём)

### 4.3 Доработка
Запустить дополнительных субагентов с заданием:
- Для отсутствующих — написать с нуля по foundation
- Для коротких — прочитать существующий текст, определить недостающие разделы по structure.md, дописать, сохранить стиль и хорошие фрагменты.

### 4.4 Фактологическая верификация (Spot-check)

**Почему это необходимо:** Субагенты склонны галлюцинировать «оживляющие примеры» — конкретные имена второстепенных персонажей, цитаты из несуществующих папирусов, точные цифры без источника, хронологические привязки реальных лиц к неверным событиям. В научно-популярной книге это недопустимо.

После Expansion провести выборочную верификацию по **5–10 наиболее подозрительным местам**:

**Что проверять в первую очередь (ранжировано по риску):**
1. **Прямая речь в кавычках** — если это не прямая цитата из известного источника (ат-Табари, Иоанн Никиусский), а «реконструкция слов исторического лица» — почти гарантированно галлюцинация. В научпопе допустима как стилистический приём, но должна быть явно помечена (например, словом «вероятно» или сноской).
2. **Имена второстепенных персонажей** — если имя не из foundation/facts.json и не из широко известного источника — проверить через Search Harvester или веб-поиск.
3. **Точные цифры** (высота стен, количество воинов, суммы дани, объём цистерн) — если нет ссылки на источник — проверить. Субагенты склонны завышать/занижать.
4. **Хронологическая привязка** — реальное историческое лицо может быть приписано к неверному периоду (например, врач, умерший за 5 лет до событий, «лечит армию»).
5. **Ссылки на несуществующие папирусные находки** — субагенты любят генерировать «коптские папирусы из Фаюма» с вымышленным содержанием.

**Инструмент верификации:** любой доступный поисковый инструмент или браузер. Возможные варианты ( зависят от конфигурации Hermes и прав пользователя):
- `web_search` (Brave Search, DuckDuckGo, Tavily, Google — зависит от провайдера)
- `browser` (поиск через браузер-автоматизацию)
- Search Harvester (локальный SearXNG + adapter, если установлен на машине)
- `web_extract` (для глубокой проверки конкретной страницы)

Отправлять конкретные запросы и проверять результаты по авторитетным источникам (Wikipedia, JSTOR, академические публикации, архивы университетов).

**Если галлюцинация подтвердилась:**
- Исправить факт (через patch к chapter-файлу)
- Или перевести в режим гипотезы («по некоторым сведениям...», «возможно...»)
- Или удалить (если не влияет на нарратив)

### 4.5 Influence Ladder для глав о наследии и влиянии

Если глава обсуждает влияние одной культуры/религии/институции на последующие традиции, все утверждения нужно раскладывать по методологической шкале. Это особенно важно для исторического научпопа: читателю нужен сильный тезис, но без ложной прямой преемственности.

**Уровни влияния:**

1. **Прямое наследие** — документированная, техническая или институциональная преемственность. Примеры: письменность, календарная практика, административная форма, юридический документ, измерительная система.
2. **Культурная передача** — мотив или форма прошли через посредников и заметно изменились. Формула: «мотив был переосмыслен», «сюжетный каркас прослеживается», «поздняя традиция переработала более ранний материал».
3. **Типологические параллели** — похожие структуры возникают в сходных условиях, но прямая линия не доказана. Формула: «сходная модель», «типологическая параллель», «общий культурный фон».
4. **Спорные аналогии** — сходство выразительное, но доказательность слабая. Формула: «соблазнительная, но спорная аналогия», «прямую линию проводить нельзя», «можно сопоставить, но не выводить одно из другого».

**Запрещённые формулы без сильного источника:**
- «X произошёл из Y»;
- «это чертёж/матрица/архетип всех последующих религий»;
- «структура осталась прежней»;
- «современная традиция напрямую унаследовала...».

**Предпочтительные формулы:**
- «один из ранних пластов»;
- «более широкий культурный слой»;
- «типологическая параллель»;
- «не прямая линия преемственности, а общий фон»;
- «мотив был переосмыслен в другом богословском/политическом контексте».
**Чистка после расширения (обязательный шаг).** После каждого прохода расширения главы проводить проверку:
```python
import re
with open('chapters/ch_XX.md') as f: text = f.read()
chinese = re.findall(r'[\u4e00-\u9fff]+', text)  # китайские символы
latin_phrases = re.findall(r'\b[A-Z][a-z]+\s+[a-z]+\b', text)  # English фразы
print(f"Китайские: {chinese}, Латинские: {latin_phrases}")
```
- Китайские символы без контекста (научные термины, географические названия) — проверить необходимость.
- Английские вставки без необходимости — заменить на русский эквивалент.
- Латинские названия (Camellia sinensis и т.п.) — сохранить как научную терминологию.
- После чистки — пересчёт word count и сравнение с целью.

**Типичные паттерны галлюцинаций (из реального кейса «Арабское завоевание Египта»):**
- Имя реального исторического лица приписано к неверному событию: аль-Харис ибн Калада (ум. 634) назван врачом при армии Амра (поход 639–642). 
- Числовые параметры завышены: стены Вавилона названы «18 метров» (реально 10 м), диаметр башен «15 м» (реально 31 м), дата основания сдвинута с Диоклетиана (ок. 300) на Траяна (нач. II в.).
- «Папирус Пафнутия» с письмом «арабы уже здесь, ничего страшного» — полностью сгенерирован, не существует.
- «Псате с 13 свиньями» — жанр папируса реален, конкретный документ не идентифицирован.

## Этап 5. Assembly

**Вход:** готовые главы.
**Выход:** `book.pdf`.

### 5.1 Сборка manuscript.md
Использовать скрипт или `pandoc`:
1. YAML frontmatter (заголовок, автор, дата, язык, геометрия)
2. `\newpage` между главами
3. `\part*` перед каждой частью
4. TOC (оглавление) — `--toc`

### 5.2 PDF

**Бумага A5** — стандарт для научно-популярных книг. При объёме ~30K слов выходит ~150 страниц.

**Сборка manuscript → PDF:**
```bash
pandoc \
  --standalone \
  --toc \
  --toc-depth=1 \
  --pdf-engine=xelatex \
  -V geometry="top=2cm,bottom=2.5cm,left=2.5cm,right=2cm" \
  -V fontsize=11pt \
  -V papersize=a5 \
  -V mainfont="Liberation Serif" \
  -V toc-title:"Оглавление" \
  -o book.pdf \
  manuscript.md
```

**Ключевые флаги:**
- `--standalone` — генерирует титульную страницу из YAML frontmatter (title, author, date)
- `--toc` — автоматическое оглавление с номерами страниц
- `--toc-title:"Оглавление"` — заголовок оглавления
- `--toc-depth=1` — только заголовки `#` (главы), подзаголовки `##` не попадают в оглавление

**Выбор шрифта:**
- `Liberation Serif` — доступен на сервере, полная поддержка кириллицы. **Рекомендуется как первый выбор.**
- `FreeSerif` — если нужны коптские/древнегреческие символы.
- `Nimbus Roman` — резервный вариант (URW Base35).

**Проверить результат:**
```bash
pdfinfo book.pdf        # страницы, размер, метаданные
pdftotext book.pdf - | head -60  # читаемость: титул → посвящение → оглавление → контент
```

**Типичная структура PDF (правильный порядок):**
1. Страница 1 — титул (название + автор + год из frontmatter)
2. Страница 2 — посвящение (пустая по layout, но с текстом)
3. Страница 3 — оглавление (auto-generated by `--toc`)
4. Страница 4+ — Введение, главы

**Рекомендуемый порядок блоков в manuscript.md:**
```
---
title: "Название книги"
author: "..."
date: "2026"
---

\newpage
\thispagestyle{empty}

*Посвящение*

\newpage

# Оглавление
[Оглавление генерируется автоматически флагом --toc]

\newpage

# Введение
...
# Глава 1. ...
...
```

---

**Питфолл: дублирование титула (КРИТИЧНО).**

Если в manuscript.md после frontmatter идёт `# Название` или `## Подзаголовок` — pandoc выводит их **после** титульной страницы, создавая дублирование. YAML frontmatter уже формирует титульный лист.

**Правило:** H1/H2 с названием книги в теле рукописи — НЕ использовать. frontmatter `title` делает всю работу. Посвящение вставить через `\newpage` + `\thispagestyle{empty}`.

**Проверка:** `pdftotext book.pdf - | head -20` — титул должен появиться ровно 1 раз.

**Также проверить:** `grep "^# " manuscript.md | head -5` — первая строка контента (после frontmatter) должна быть `# Оглавление` или `# Введение`, а не `# Название книги`.

### 5.3 Сборка через скрипт (рекомендуется для книг с частями)

Вместо ручной конкатенации используйте Python-скрипт `scripts/build_manuscript.py`, который:
- Вставляет `\part{}` перед каждой частью
- Добавляет `\newpage` между главами
- Генерирует YAML frontmatter с метаданными
- Позволяет задать последовательность (части + главы)

### 5.4 Ручная вставка оглавления (только для HTML/md, не для PDF)

`--toc` генерирует оглавление **автоматически** при сборке PDF. Ручные markdown-ссылки с якорями (`[Глава 1](#глава-1)`) в manuscript.md — **не нужны**, они работают только для HTML, а в PDF дублируют то, что делает `--toc`.

**Когда нужны ручные якоря:**
- Экспорт в HTML (e.g., via `--to html` или GitBook-хостинг)
- Пользователь просит интерактивное оглавление в markdown-файле

В этих случаях — добавить `<span id="глава-N">` после каждого заголовка:
```markdown
# Глава 1. Первые храмы Эриду
<span id="глава-1"></span>
```

**Стандартный порядок (рекомендуется):** править manuscript.md → запускать `pandoc --toc` → PDF с auto-generated TOC. Ручное оглавление в markdown не обязательно.

### 5.5 Постпроцессинговая ревизия рукописи (после вычитки субагентами)

После сборки `manuscript.md` и получения отчётов вычитки — **обязательный этап исправления критических проблем**. Это не optional: субагенты находят реальные ошибки.

**Порядок действий (7 шагов):**

1. **Сканирование иноязычных вкраплений.** English-слова внутри русского текста — систематический фейл субагентов. Регулярка: `\b[a-zA-Z]{3,}\b` по всему файлу. Оставлять только: транслитерации (gidim, ziqqurratu, Ilum), латинские термины (primae noctis), римские цифры, URL, научные термины (ETCSL). Таблица типичных замен — `references/cleanup-patterns.md`.

2. **Поиск дублирующегося контента.** Одна и та же тема в разных главах (например, Потоп в Гл.9 и Гл.11) проверяется через поиск ключевых фрагментов. Если текст почти идентичен — сокращать вторичную главу, сохраняя уникальный материал. Проверять: Потоп, Эдем, Сотворение мира, Священный брак.

3. **Мосты между главами.** Искать места где нарратив обрывается. Проверять: конец каждой главы → начало следующей. Если перехода нет — вставить 2–3 предложения моста перед `# Глава N`. Текст моста должен отвечать на вопрос: «К чему это ведёт? Почему это важно для следующей темы?».

4. **Расширение библиографии.** Если в библии <6 источников — добавить. Минимум: 2 первичных (ETCSL или аналог), 4–6 научных (Крамер, Якобсен, Боттеро + 2–3 современных). Обязательно: годы публикации в скобках.

5. **Стандартизация заголовков.** Проверить все `##` заголовки: единый формат (двоеточие или точка, не смешивать), нет English-фраз в заголовках. Обычная ошибка: `## Крючок: Британский музей, 1872 год` — если этот хук уже был во Введении, в главе должен быть **мост**, а не второй хук.

6. **Хук во Введении.** Если вычитка указала на отсутствие хука — добавить кинематографичную сцену (1–2 страницы) перед изложением тезисов. Идеальный хук: конкретная сцена с датой, местом, именем и действием.

7. **Финальная сборка и проверка.** После всех правок — пересборка manuscript.md и финальный подсчёт слов. Целевой диапазон: target ±5%.

**Ключевой принцип хуков:** Хук — кинематографичная сцена с конкретным местом, временем и действием. Мост — 2–3 предложения, объясняющие связь с предыдущей/следующей темой. В книге должен быть **один главный хук** (во Введении). Каждая глава начинается с **моста**, а не с хука. Исключение: если синопсис явно требует хук для конкретной главы (например, глава об Инанне начинается со сцены её нисхождения в Кур) — это допустимо, но только если такого хука нет во Введении.

**Быстрая проверка заголовков:**
```bash
grep "^## " manuscript.md | head -30
```
Все заголовки должны быть на русском, без English-фраз (кроме римских цифр и научных терминов).

**Чеклист перед финальной сборкой:**
- [ ] CJK = 0
- [ ] English-слов (реальных) ≈ 0
- [ ] Нет дублирующегося контента
- [ ] Мосты между всеми главами
- [ ] Библиография ≥ 6 источников
- [ ] Заголовки стандартизированы
- [ ] Хук во Введении
- [ ] Word count в диапазоне
- [ ] LaTeX/patch-артефакты удалены

## Применение редакторской рецензии (ручной patch-проход)

После того как внешний рецензент (или ведущий агент) выдал список замечаний с точными цитатами и рекомендуемыми формулировками, выбирай режим правки по масштабу:

- **≤3 точных места** — только ручной micro-final patch, без субагентов и без широкой чистки.
- **4–10 точных мест** — ручной patch-проход ведущим.
- **5+ категорий проблем** — можно запускать субагентов по категориям, но после них обязателен контроль структуры ведущим.

Не используй субагентов для микрофинальных правок: они могут переписать больше, чем нужно, или внести структурные дефекты.

### Micro-final pass rule

Если рецензия говорит «осталось только N мест» или пользователь просит «исправить только эти пункты»:

1. Создать todo ровно из этих пунктов.
2. Для каждого пункта прочитать контекст `read_file(offset, limit)`.
3. Внести только точечный `patch(mode=replace)`.
4. Проверить, что старые фразы исчезли через `search_files`.
5. Не запускать broad cleanup, style pass, rewrite pass, expansion.
6. Сразу собрать финальные `.md`/`.pdf` и отправить.

**Stop condition:** завершить книгу, если выполнены условия:
- критических фактологических ошибок не осталось;
- оставшиеся вопросы требуют внешнего специалиста, а не LLM-редактуры;
- рецензия достигла целевого уровня для авторской публикации;
- пользователь просит закругляться;
- дальнейшие правки — вкусовые, а не структурные/фактологические.

### Протокол

1. **Прочитай рецензию целиком** — выдели все места, где указаны конкретные старый/новый текст.
2. **Для каждой правки** — прочитай контекст вокруг целевого текста через `read_file(offset, limit)` с запасом ±10 строк. Убедись, что old_string уникален и не заденет соседние абзацы.
3. **Используй `patch(mode=replace, old_string, new_string)`** — это безопаснее `sed`, потому что требует точного совпадения и не сломает структуру файла.
4. **Веди учёт через `todo`** — создай список всех правок, отмечай их `in_progress` → `completed`.
5. **Верифицируй** — после всех правок запусти `search_files(path=manuscript.md, pattern=...)` для каждого удалённого/заменённого оборота. Убедись, что старые фразы не остались.

### External Review Ingestion

Когда пользователь присылает внешнюю рецензию (`review.md`, `chatgpt_*.md`, редакторский отчёт), сначала преврати её в рабочую карту правок.

**Алгоритм:**
1. Извлечь текущую оценку, целевую оценку и статус («черновик», «почти финал», «финал после микроправок»).
2. Разбить замечания на категории:
   - critical factual;
   - terminology/entities;
   - structure/composition;
   - influence/overclaiming;
   - reconstruction/quotes;
   - tone/style cooling;
   - microcopy/proofreading;
   - production/PDF.
3. Создать todo по категориям.
4. Если категория содержит точные старый/новый текст — патчить вручную.
5. Если категория требует анализа целой главы — можно дать субагенту только эту категорию и только эту главу.
6. После всех правок — контрольный проход ведущим: структура `grep "^# "`, старые фразы, word count, PDF.

**Правило приоритета:** critical factual > terminology > overclaiming > structure > style > proofreading > PDF.

### Five-pass final editing protocol

Финальная редактура исторического научпопа проходит не одним «улучши текст», а пятью разными проходами:

1. **Structural coherence:** дуга книги, порядок глав, повторы, мосты, перегруженные блоки.
2. **Terminology/entities:** имена, должности, города, термины, варианты написания, запретные связки.
3. **Fact-risk cleanup:** даты, экспедиции, точные числа, археологические находки, абсолютные первенства, прямые линии влияния.
4. **Style cooling:** убрать чрезмерную публицистику, офисные/технологические анахронизмы, «самое важное/интересное», перегретые метафоры.
5. **Production:** микровычитка, структура заголовков, `.md`, PDF, проверка `pdftotext`.

Не смешивать все пять проходов в одном субагентском задании: это повышает риск структурных поломок.

### Modern metaphor and anachronism audit

Перед финальной сборкой искать современные метафоры, которые снижают тон исторического научпопа или создают анахронизм:

```regex
корпорац|директор|KPI|ключевые показатели|стартап|Uber|Facebook|алгоритм|интерфейс|база данных
```

Не все такие слова запрещены, но каждое должно быть оправдано. Предпочтительные замены:
- «хозяйственная система»;
- «центр учёта»;
- «административная машина»;
- «ритуальное обслуживание»;
- «архив наблюдений»;
- «практика управления».

## Post-Editing LaTeX/Patch Artifact Cleanup

## Питфоллы

0. **Subagent-делегация: диагностика и workaround (актуально на 2026-05-02).** `delegate_task` может возвращать `HTTP 404 — Not Found | opencode` по двум независимым причинам:

   **Причина 1 (транспортная):** `_resolve_delegation_credentials` вызывается БЕЗ `target_model`, что для провайдера `opencode-go` ведёт к неправильному `api_mode = anthropic_messages` и `base_url = https://opencode.ai/zen/go` (без `/v1`). Запрос попадает на эндпоинт Anthropic-совместимого API, который возвращает 404 + HTML.
   
   **Причина 2 (reasoning-модель):** `deepseek-v4-flash` — reasoning-модель. Без `{"thinking":{"type":"disabled"}}` весь ответ кладётся в `reasoning_content`, а `content` остаётся пустым. Парсер Hermes получает пустую строку → ошибка парсинга.

   **Рабочий workaround (подтверждён 2026-05-02):** В `~/.hermes/config.yaml` добавить секцию `delegation` с явным `base_url`:
   ```yaml
   delegation:
     base_url: 'https://opencode.ai/zen/go/v1'
   ```
   При наличии `delegation.base_url` функция `_resolve_delegation_credentials` полностью обходится — subagent сразу получает правильный `base_url`, `api_mode = chat_completions`, и HTTP-запрос уходит на нужный эндпоинт.
   
   Также в `~/.hermes/.env` должен быть установлен `OPENAI_API_KEY` (или `OPENCODE_GO_API_KEY`) с тем же ключом.

   **Проверка работоспособности** (перед запуском NFP):
   ```bash
   source ~/.hermes/.env
   curl -s -X POST https://opencode.ai/zen/go/v1/chat/completions \
     -H "Authorization: Bearer $OPENAI_API_KEY" \
     -H "Content-Type: application/json" \
     -d '{"model":"deepseek-v4-flash","messages":[{"role":"user","content":"Say OK"}],"max_tokens":10,"thinking":{"type":"disabled"}}'
   ```
   Если в ответе `"content":"OK"` — subagent-делегация работает.

   **Детальная диагностика и хронология:** `references/subagent-delegation-failure.md`

   **Fallback (если workaround не сработал):** прямое написание через `execute_code` + `write_file`. Темп: 1 500–2 500 слов/вызов. Подробности — см. пункт Fallback ниже.

   **Fallback: по главе за раз, итеративное расширение.** Если ACP сломана ИЛИ пользователь явно попросил работать без субагентов — работаем напрямую через `execute_code`:
   1. Считать текущий word count. Если <99 % цели — писать дополнение в конец файла (`append` через `open(path, 'a')`, НЕ перезаписывать существующий текст).
   2. После каждого расширения — чистка (cм. ниже).
   3. Повторять пока глава не достигнет ≈95–99 % целевого объёма.
   4. Только после этого — сборка `manuscript.md` и переход к следующей главе.

   **Почему append, а не перезапись:** при перезаписи через `write_file` модель может невольно удалить хороший существующий текст. Append гарантирует сохранность. Расширяем пока суммарно не достигнем цели.

   **Чистка после расширения (обязательный шаг, ВСЕГДА).** Подробные паттерны и скрипт — `references/cleanup-patterns.md`. Краткий порядок:
   
   ```python

   with open('chapters/ch_XX.md') as f: text = f.read()
   lines = text.split('\n')
   for i, line in enumerate(lines, 1):
       has_cyrillic = bool(re.search('[а-яА-ЯёЁ]', line))
       has_latin = bool(re.search('[a-zA-Z]', line))
       has_chinese = bool(re.search(r'[\u4e00-\u9fff]', line))    # китайские
       has_japanese = bool(re.search(r'[\u3040-\u30ff]', line))     # японские
       if (has_cyrillic and has_latin) or has_chinese or has_japanese:
           print(f"Строка {i}: {line[:70]}")
   ```

   3. English-фразы (2+ слова) в русском контексте → заменять на русский эквивалент.
   4. Римские цифры (XVII, XVIII) — оставлять как есть.

## Структурные дефекты после субагентного патчинга

Помимо мусорных строк (`\\newpage`, `bridge`, `header`), субагенты-патчеры вносят **структурные** дефекты:

### 1. Дублированные заголовки
Два одинаковых `## Название секции` подряд — результат патча, который удалил текст между ними, но оставил заголовок.

**Диагностика:** `grep -n "^## " file.md | sort | uniq -d` — найти дубликаты.
**Лечение:** вручную (через `sed -i 'Nd'` удалить строку N) — автоматика небезопасна.

### 2. Секция перед `# Финал` без перехода
`## Что осталось от богов` + сразу `# Финал: Глина и звёзды` — заголовок секции оказывается перед заголовком главы, что ломает логику. Лечение: убедиться что `# Финал` — это последний элемент книги, а секция перед ним — часть последней главы.

### 3. Археологические заметки после эмоционального финала
Глава заканчивается сильным эмоциональным/нарративным финалом → идёт `## Археологическая заметка: цифры и факты` (5-10 предложений) → глава обрывается. Это убивает ритм.

**Лечение:** ключевой факт из археологической заметки (1-2 предложения) встроить в последний абзац финала; остальное — удалить. Пример: «Высота зиккурата Ура — 25–30 метров, основание 62×43 м. На строительство пошло ~7 млн кирпичей. Тень зиккурата падала на Месопотамию тысячи лет» → встроить в последний абзац, `## Археологическая заметка` удалить.

### 4. Двойные финалы главы
Глава заканчивается эмоционально → ещё один абзац → ещё один → «археологическая заметка». Финал должен быть один сильный.

**Лечение:** выбрать последний нарративный абзац → всё что после — либо встроить в него, либо удалить.

   **Реалистичные ориентиры объёма при fallback (MiniMax-M2.7):**
   - Один вызов `execute_code` → write_file: ~1 500–2 500 слов за раз.
   - Глава ~3 000 слов требует 2–3 итераций расширения (каждая итерация ≈ +500–900 слов).
   - Книга из 10 глав (~30 000 слов) требует ~15–20 вызовов.
   - На каждую главу: 2–3 прохода расширения + 1 чистка.

1. **Таймауты субагентов** — самая частая проблема. Даже при 2–3 главах на субагента время 900 с может быть недостаточным. **Не паниковать:** это ожидаемо. Перейти к Expansion (Волна 2), проверить chapters/ на частичные файлы.
2. **Отсутствие foundation** — без voice/terms/facts субагенты пишут в разном ключе.
3. **Повторы** — при расширении главы не удалять существующий текст, только дополнять.
4. **Мосты между главами** — обязательны для плавности; проверить в самом конце.
5. **Шрифты в PDF** — если DejaVu не установлен, заменить на Liberation Serif или Noto Serif. Для книг с нелатинскими/некириллическими скриптами (коптский, греческий, иврит) использовать FreeSerif.
6. **Синопсис от пользователя** — если он детальный, фаундейшн извлекается, а не пишется с нуля. Скопировать синопсис в assets/synopsis.md как референс для субагентов.
7. **Проверка после таймаута** — всегда проверяй `ls chapters/` перед перезапуском: файлы, успевшие записаться до таймаута, остаются на диске.
8. **Запрет удаления в expansion** — явно указывай субагенту: «Ничего не удаляй из существующего текста. Только дописывай новые разделы в конец». Без этой инструкции субагенты могут переписать главу заново.
9. **Галлюцинации в «оживляющих примерах»** — субагенты склонны генерировать вымышленные имена, папирусные цитаты, точные числа без источника. Всегда проводить Spot-check верификацию (см. Этап 4.4). Особенно уязвимы: прямая речь в кавычках, имена второстепенных персонажей, точные цифры, хронологическая привязка реальных лиц.
9. **Заголовки разделов в TOC** — если внутри глав используются подзаголовки вида `## I`, `## II`, Pandoc выведет в оглавление «I», «II» — бессмысленно. Всегда давать разделам содержательные названия: `## I. Смерть Ираклия: три акта трагедии`. Проверить перед финальной сборкой manuscript.md через `grep "^## "`.

10. **Сборка через скрипт (рекомендуется)** — при ручной конкатенации легко пропустить `\part{}` разрывы между частями книги. Использовать `scripts/build_manuscript.py` с явным списком последовательности. Проверить `grep "^# Глава\|^\\\\part" manuscript.md` после сборки.

11. **Заключение — особая глава** — у него иная природа, чем у нарративных глав. Это эмоциональный финал, а не информационный блок. Реалистичный объём: 1 500–2 000 слов (не 3 000). quality gate: <500 слов — критически мало, требует расширения. Целевой порог: ≥1 500 слов. Заключение нельзя «добивать» тем же методом, что главы — оно требует цельного переписывания, а не наращивания.

12. **facts.json — валидация и ремонт** — структура файла: `{"metadata": {...}, "facts": [...]}`. Это **словарь с двумя ключами**, а не плоский массив. Распространённые ошибки при ручном редактировании:
    - Одинарные кавычки как разделитель строки (`'значение'`) — невалидный JSON. Все строковые значения должны быть в двойных кавычках.
    - Внутренние кавычки в тексте (например, прямая речь внутри `verification_note`) должны быть экранированы: `"сказал он"` → `\"сказал он\"` в JSON.
    - Фигурные юникод-кавычки (`„` U+201E, `"` U+201C) могут появляться при копировании из Word/Google Docs и нарушать валидность.
    - Валидация: `python3 -c "import json; json.load(open('facts.json'))"`
    - Полный ремонтный протокол — `references/facts-json-repair.md` (byte-level диагностика, паттерны ошибок, порядок действий).

13. **CJK-символы при генерации русского текста** — LLM может вставлять китайские/японские символы (`大多数`, `同時`, `に`) внутрь русского текста при expansion. Это систематический фейл-мод, а не разовая ошибка. После любого изменения файла главы запускать проверку:
    ```python
    import re
    with open('chapters/ch_XX.md') as f: text = f.read()
    cjk = re.findall(r'[\u4e00-\u9fff\u3040-\u309f\u30a0-\u30ff]', text)
    if cjk: print(f"CJK найдены: {set(cjk)}")
    ```
    Все китайские символы в русском тексте заменять на русский эквивалент.

14. **LaTeX/patch-артефакты после субагентного редактирования** — после каждого прохода субагента на патчинг manuscript.md в файле остаются мусорные строки: `\newpage`, `\thispagestyle{empty}`, `bridge`, `header`, `removed`, `<span id=...>`, `</span>`, `pandoc auto generates`. Перед отправкой файла пользователю выполнить чистку:
    ```python
    import re
    path = "manuscript.md"
    with open(path) as f: text = f.read()
    for junk in ['\\newpage', '\\thispagestyle{empty}', 'pandoc auto generates',
                 'removed', 'bridge', 'header', '<span id=', '</span>']:
        text = text.replace(junk, '')
    text = re.sub(r'  +', ' ', text)
    text = re.sub(r'\n{3,}', '\n\n', text)
    with open(path, 'w') as f: f.write(text)
    ```

15. **German/Spanish truncation artifacts** — при патчинге строк с русскими окончаниями и оборванными EN/DE/ES-фрагментами характерны маски: `Рихарда Хай1970-х годах` (Хайнрих + год), `their{ая}` (English-слово в скобках), `proyectают` (испанское слово в русском), `übernели` (German-префикс в русском), `мірського` (украинизм). Регулярное выражение для поиска: `\b[a-zA-Z]{3,}[а-яА-ЯёЁ]{1,3}\b` — найти все such mixed-script transitions и исправить.

16. **Editorial review passes — координация 4+ субагентов параллельно.** Внешняя рецензия (7–8/10) выявляет 5–8 категорий проблем. Оптимальная стратегия — запускать **4 субагента одновременно**, каждый на свою категорию, затем финальная дошлифовка ведущим. Категории: (1) техническая чистка, (2) переструктурирование перегруженной главы, (3) фактологические оговорки, (4) терминология и стиль, (5) сокращение конкретных глав. При волне 4 субагентов — обязателен контрольный проход ведущего после их завершения (субагенты могут вносить структурные дефекты: дубли заголовков, потеря секций, артефакты склейки). Патч-файл ведущего занимает 1–2 правки, но требует чтения контекста вокруг каждой правки.

17. **Дублирование контента между waves.** Субагент волны 2 может добавить секцию, которая уже существует в файле (например, библиографию). Всегда перед финальной отправкой — `grep -n "## Библиография\|## Что осталось\|# Финал\|# Примечания"` — проверить порядок и отсутствие дубликатов.

## Subagent Configuration

Субагенты используют настроенный провайдер из `config.yaml`. Конфигурация должна быть такой:

**`~/.hermes/config.yaml`:**
```yaml
delegation:
  model: deepseek-v4-flash
  provider: opencode-go
  base_url: 'https://opencode.ai/zen/go/v1'   # ← критично, без /v1 не работает
  api_key: ''                                  # ← берётся из .env
  max_iterations: 50
  child_timeout_seconds: 900
  reasoning_effort: low
  max_concurrent_children: 3
```

**`~/.hermes/.env`:**
```
OPENAI_API_KEY=sk-...        # тот же ключ, что и OPENCODE_GO_API_KEY
OPENCODE_GO_API_KEY=sk-...
```

**Ключевой момент:** секция `delegation.base_url` обходит `_resolve_delegation_credentials` полностью. Без неё функция вызывается без `target_model` и получает неправильный `api_mode` + `base_url` → HTTP 404.

**Pre-flight проверка перед запуском NFP:**
```bash
source ~/.hermes/.env
curl -s -X POST https://opencode.ai/zen/go/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek-v4-flash","messages":[{"role":"user","content":"TEST"}],"max_tokens":10,"thinking":{"type":"disabled"}}'
```
Ожидаемый ответ: `"content":"TEST"`, `finish_reason:"stop"`. Если `"content":""` и `finish_reason:"length"` — reasoning-модель не получила `thinking:disabled`, нужно проверить конфигурацию.

**Лимит параллельных субагентов:** `max_concurrent_children: 3` (default). 2–3 главы на одного субагента — оптимально для избежания таймаутов.
